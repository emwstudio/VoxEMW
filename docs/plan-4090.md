# VoxEMW 满血版方案（4090 / 24GB）

> 2026-08-28 立项。主线从 Mac+VRM 二次元版（存档于 git tag v1.9.0）迁移到 4090 写实满血版。

## 架构总图

```
浏览器 / iPhone（纯客户端：麦克风上行 WS + 摄像头抓帧 + 视频播放）
        │  ws/http（TCP-only 隧道时下行音频也走 WS；LAN/公网可走 WebRTC）
        ▼
4090 服务器（24GB，AutoDL 北京 B2 已跑通）
  orchestrator（:8000 + LAN TLS）——会话调度，代码照旧
    ├─ s2s 管线（:8765）：Silero+SmartTurn → Qwen3-ASR-1.7B-hf → DeepSeek API → VoxCPM2
    ├─ SoulX-FlashHead-1_3B 视频服务：TTS 音频流 → 写实数字人视频帧
    └─ vLLM serve MiniCPM-V-4.6（眼睛，OpenAI 兼容接口）
```

## 模型选型（全部 2026 最新）

| 积木 | 模型 | 备注 |
|---|---|---|
| VAD | Silero + SmartTurn v3.2（CPU ONNX） | 不动 |
| STT | Qwen/Qwen3-ASR-1.7B-**hf** | 必须用 -hf 变体（见「踩坑记录」#3），device 走 CUDA |
| LLM | DeepSeek v4-flash API | 不动 |
| TTS | openbmb/VoxCPM2（官方 PyTorch+CUDA，load_denoiser=False） | 新写 tts_voxcpm2 handler，48k→16k 重采样 |
| 数字人 | Soul-AILab/SoulX-FlashHead-1_3B | 音频驱动 image-to-video，写实脸用 AI 生成 |
| 眼睛 | openbmb/MiniCPM-V-4.6（vLLM serve） | 绕开 transformers 原生 bug；摄像头改客户端抓帧 |

## 显存预算（24GB）

Qwen3-ASR-1.7B ~4.7G + VoxCPM2 ~8G + SoulX ~6.4G + VLM ~2.6G + VAD ~0.5G ≈ 22G（顶格可行；
超了把 VLM 降 q4 或按需卸载）。

## 实施阶段

1. 开机器装环境（CUDA 12.x + venv + speech-to-speech + vllm + diffusers），模型走镜像拉取
2. 语音链路：STT 1.7B + tts_voxcpm2 handler + DeepSeek → 浏览器能聊
3. 视频链路：SoulX 服务 + RTC 视频轨 + 前端视频皮肤 + pacer audio_lead 音画同步
4. 眼睛：vLLM + 客户端抓帧 + 视觉回合注入
5. 联调压测：延迟/画质/稳定性实测报告

## 延迟预算

STT 0.3~0.5s + DeepSeek ~0.6s + VoxCPM2 TTFA ~0.3~0.5s + SoulX 首帧 ~0.3s + 网络 RTT
≈ 1.5~2.2s 到「开口+露脸」。

## 风险预案

- SoulX 工程化新（2026-02 开源）→ 退 MuseTalk（LiveTalking 现成后端）
- 显存顶格 → VLM 降 q4 / 按需卸载
- Mac 版存档 v1.9.0，随时可回滚

## 进展日志

### 2026-08-29：语音链路在 AutoDL 4090 全通（浏览器实测通过）

**实例**：AutoDL 北京 B2，4090D 24GB（`pro-78792e0e94b5`），
`ssh -p 46729 root@connect.bjb2.seetacloud.com`（免密已配）。
conda env `py312`（py3.12 + torch 2.13.0+cu130 + vllm 0.28.0）。
模型在 `/root/autodl-tmp/models/`（ModelScope 拉取，同云骨干 12MB/s+）+
HF 缓存 `HF_HOME=/root/autodl-tmp/hf`。

**speech-to-speech 版本**：PyPI 0.2.12 仍是老工厂 API（无 backend_registry），
我们的代码对的是 main @5a0c79f。PyPI 装不了 git 提交（构建依赖拉取失败/静默退出），
正解：`git clone` 到 `/root/autodl-tmp/speech-to-speech-src` 后
`pip install --no-deps --no-build-isolation <路径>`（0.2.12 的依赖已铺好）。

**架构变更：TCP-only 链路放弃 WebRTC，下行音频走 WS**。
AutoDL 只映射 TCP 端口，浏览器经 SSH 隧道访问时 WebRTC 的 UDP 媒体无路可走
（服务端 host candidate 是容器内网 172.17.0.9，ICE 永远卡 checking）。
`rtc.enabled: false` → orchestrator 不再剥音频 delta，前端 WebAudio 队列
续播（`wsPlayer`，打断本地清队与 speech_started 同步）。上行麦克风本来就走
WS，不动。Mac/LAN 部署仍回 `rtc.enabled: true`（低延迟 Opus 轨）。

**实测**（scripts/s2s_text_probe.py，文本注入回合录音）：
- 首轮 TTFA 1.21s（含 WS 连接）；剧本四轮全对（中/得劲儿/大信球/俺不中嘞）
- VoxCPM2 流式 TTFA 0.24s，RTF 0.40；首轮加载编译 117s（后续进程内复用）
- 显存：管线常驻 11.4GB（ASR-hf + VoxCPM2 + VAD + 连接池）

**踩坑记录**（都很值钱，别再踩）：
1. `pkill -f` 的 pattern 不能出现在自己的 ssh 命令行里（同命令行里有启动命令的
   真实名字就自杀），用方括号 trick：`'voxemw.pipeline.launc[h]'`；且杀和启分两条 ssh。
2. HF 下载：`HF_HUB_DISABLE_XET=1` + `source /etc/network_turbo`，缺其一就
   401/卡死；ModelScope SDK 更快但更吃磁盘双份。
3. **Qwen3-ASR 非 -hf 仓是 thinker.\* 键布局**，transformers 5.16 的
   qwen3_asr 实现期望 `model.audio_tower.*`——加载不报错但 audio_tower/projector
   全部 MISSING 随机初始化，前向时才炸「Audio features and audio tokens do not
   match, tokens: 13, features: 13」（计数相等、维度不等）。换 `-hf` 后缀仓即可。
4. `continue_final_message=True` 在 transformers 5.16 与该模板不兼容（渲染结果
   不含末条消息直接 ValueError）→ 热词预填改手工拼：
   `apply_chat_template(tokenize=False, add_generation_prompt=True) + "language Chinese<asr_text>"`。
5. backend_registry 的 BackendSpec.config_type 复用同一个 dataclass 会触发
   argparse 选项串冲突——STT/TTS 各用各的空壳参数类。
6. 自定义 TTS 工厂要从 HandlerContext 补传 `should_listen`（内置后端走
   `setup_args=(ctx.should_listen,)`）。
7. 上游 @5a0c79f 已删 `remove_markdown` 且 SPEECHABLE_PATTERN 自带 CJK 标点——
   旧 `_patch_text_filters` 整个拆掉；舞台指示（（乐））剥离挪进
   tts_voxcpm2.process 的句子级入口（delta 级括号对会被 token 切开）。
8. nltk punkt_tab zip 损坏（BadZipFile）是之前中断的下载留的尸，
   `rm -rf /root/nltk_data/tokenizers/punkt_tab*` 重下。
9. 会话槽位只有 1 个：浏览器会话活着时探针直连会被 1008 秒拒，先 restart
   orchestrator 再放探针。

**待办**：联调压测、发布。

### 2026-08-29（深夜）：数字人视频链路全通

**SoulX-FlashHead 环境**（独立 conda env `flashhead`，与管线 py312 隔离）：
py3.10 + torch 2.7.1+cu128 + requirements + flash_attn 2.8.0.post2（预编译 wheel）
+ ffmpeg（conda-forge）。官方仓 clone 在 `/root/autodl-tmp/SoulX-FlashHead`，
权重 `/root/autodl-tmp/models/SoulX`（Lite）+ `wav2vec2-base-960h`。
参考脸 `assets/henannier/face_ref.jpg`（Z-Image 生成的写实河南妮儿正脸）。

**实测**：样片（9s 参考音驱动）rc=0，Lite 每 chunk（24 帧/0.96s）生成 0.266s
≈ 3.6x 实时；512x512@25fps；显存峰值 ~6GB；眨眼/微表情自然，唇形跟音频。

**架构**（voxemw/avatar/soulx_server.py，新）：
渲染服务独立进程（flashhead env，ws://127.0.0.1:8791）：音频 chunk 队列 →
JPEG 帧流。orchestrator 作为客户端接入：TTS pcm 按【播放时刻】paced
（32000B/s）喂入（`Session._avatar_pacer`），帧流二进制原样转发浏览器；
打断双清（喂入队列 + 渲染队列 flush）。前端 canvas 逐帧绘制 + wsPlayer
按 response 级 lead（`avatar.audio_lead_ms=1300`）压后首块播放对齐唇形。
无音频时服务喂静音 → 待机呼吸/眨眼，数字人常活。

**无头实测**（scripts/avatar_probe.py）：vox.status avatar.enabled=true，
两轮对话帧流 25fps 稳定，抽帧确认从待机微笑→眨眼→张嘴说话的完整过程。

**一键启动**：`bash scripts/start_4090.sh`（stop 参数全停）。
启动顺序：管线(py312) → SoulX(flashhead) → VLM 边车(vlm) → orchestrator(py312)。

**视觉已上线**（2026-08-29 上午，推翻了昨晚「暂缓」的误判——
MiniCPM-V-4.6 是 1.3B/2.6GB，不是按 4.5 代 8B 估的 16G）：

- 边车：`voxemw/gateway/vlm_server.py`（transformers 原生 + FastAPI，
  OpenAI 兼容 /v1/chat/completions，:18099）。**没用 vLLM**：vllm 0.28 的
  MiniCPMV4_6 权重映射有 bug（分体 k_proj 对不上融合 qkv_proj，加载即
  ValueError）。1.3B 模型 + 低频触发，transformers 直跑足够。
- **跑在独立 vlm env（transformers==5.7.0）**：5.16.1 的 MiniCPMV4_6
  窗口合并向量化在非均匀切片下 reshape 必炸（5.16 回归，5.7.0 正常）。
  36 切片细节档已恢复——OCR 实测（标题/口号/数字串）逐字全对。
- 官方输出后处理 `normalize_response_text` 已吸收（模型偶发把换行
  输出成字面量 \n，OCR 场景必现）。
- 磁盘事故：镜像盘 108G 曾打满（HF 缓存重复 + pip 缓存 20G），已清：
  HF 里的 SoulX/非-hf ASR 死缓存、ModelScope 重复权重、pip cache purge。
  现役占用 ≈ 62G。
- 推理定式照模型卡：`AutoModelForImageTextToText` + apply_chat_template
  一体化 tokenize + `downsample_mode="16x"`（generate 时也要传）。
- FastAPI 坑：`from __future__ import annotations` 把注解变字符串，
  函数体内 import 的类型 FastAPI 解析不到会降级成 query 参数（422
  "query req Field required"）——web 框架相关 import 一律模块级。
- 帧源：服务器没摄像头 → 浏览器 getUserMedia 每 1.5s 上传 640px JPEG
  （POST /vision/frame，存在 Session._last_frame）；说「看看」时
  `_vision_turn` 掐自动回复 → 取 <10s 的帧 → VLM 描述 → 注入人设口吻重答。
- 四模型同卡实测：管线 11.4G + SoulX ~6G + VLM ~2.7G ≈ 20.3G / 24G。

**待查**：SoulX 服务 8-29 凌晨曾莫名退出（日志无 traceback，dmesg 无 OOM
记录），已重启观察；若复现需加看门狗。

### 2026-08-29（下午）：显式同步弯路与 V1 回滚（架构决策记录）

**走了什么弯路**：为把开口延迟从 3.2s 压到 ~2.6s，把 V1（paced 喂入 +
服务端 25fps 滴灌 + 前端到达即画，单时钟隐式同步）改成显式同步
（生成速度喂入 + 帧带 4B 时间戳 + 前端游标排程）。引入时间戳账务
（fed/consumed/origin）、response_start/end 协议、warp/游标曲线，
一天修 ~10 个 bug（归零竞态、静音半块污染、负时间戳、顺延帧、
接缝停顿、游标符号写反……），最终 lead 却从 0.8 一路加回 1.35s
≈ V1 的 1.3s——**延迟目标没有达成，复杂度全款付清**。

**教训（用户拍板回滚）**：真实约束（张嘴过渡 0.5s 必须装进 lead 窗口、
TTS 抖动余量）不随架构改变。V1 的 1.3s lead 就是物理下限，「快 0.5s」
不值一倍复杂度。已回滚（commit 6212d71）：paced 喂入 + 滴灌 + 到达即画，
lead 1300ms；保留两项正资产：flush 在攒段循环内即丢（57a6e38）、
avatar 断线自动重连+会话收尸（d9c61ac）。

**最终形态（用户验收「这个就很好」）**：
- 开口 ~3.2s（思考链 1.9s + lead 1.3s），唇形由 paced 时钟天然对齐
- 待机呼吸常活、打断双清、收尾收嘴（补静音尾帧标待机帧+只留 6 帧）
- 张嘴过渡（模型固有 ~0.5s 从闭嘴续接）在 lead 窗口内自然演完

**Qwen3.8-27B 评估（用户提议，已否）**：27.8B VLM 确实能当眼+脑，
但当不了「脸」（无视频生成能力，SoulX 无法被替）也发不了声；
Q4 ~16G + ASR + TTS ≈ 28.7G 爆显存；全双工是管线属性（打断已实现），
与模型无关。本地大脑方向若要试，现实选项是 8B 级（~5G），代价是人设质量。
